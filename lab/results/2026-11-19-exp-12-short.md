# Experiment #12, entry 4: short subjects, time per call

> Erratum: the VS Code calls per pass is 198,837 (`ocaml-re` 192,444), not 759,850; the crossing figure is an upper bound including harness dispatch. See [entry 10](2026-11-19-exp-12-review-fixes.md).

**What.** Criterion 2, short-subject shape: time per call and words
allocated per call for six columns (C-only driver, `[@@noalloc]` stubs,
ctypes, VM `ffi`, VM `ffi-flambda`, `ocaml-re`) on the in-subset,
VM-agreeing calls of jq, PHP and VS Code, plus experiment #1's
long-subject PHP sample as a labelled synthetic row.

**Why.** Many short searches is the VS Code tokenizer's shape; here the
FFI crossing is paid once per search and is most visible.

## Provenance

As [entry 1](2026-11-19-exp-12-provenance.md). Command:
`EXP=<exp> python3 -I run.py short r1 10`, 2026-11-19 17:12-17:14 UTC.
Each run of a cell is one process under `taskset -c 2` and
`timeout 120`: one untimed warm-up pass over the family's calls, then
whole passes repeated until 0.5 s has elapsed (`Mtime_clock`, monotonic;
`clock_gettime(CLOCK_MONOTONIC)` in the C driver). Each call is repeated
`weight` times per pass (VS Code: the frequency-profile count). 10
interleaved runs: run r visits the 24 cells in an order shuffled with
seed r. Load average 0.29-1.04 over the series; no other experiment
detected. No cell exceeded the 10% IQR gate, so none was repeated.

Calls per pass: jq 136, PHP 158, VS Code 759,850 (123,982 distinct
searches), long PHP 11 (30,000-byte and 2 MiB subjects). `ocaml-re`
skips the calls it cannot express (VS Code: 3,838 of 123,982), so its
row covers a different, smaller set and is a reference only.

## Analysis

- **FFI crossing, stubs:** +3.5 ns (jq), +7.8 ns (VS Code) per call;
  within noise on PHP (-15 ns, calls dominated by matching time);
  +1.1 µs (+7%) on the long PHP sample, whose subjects are large
  (no copy: the gap there is unexplained, possibly code alignment or
  cache effects of the OCaml process, and is noted as such).
- **FFI crossing, ctypes:** about +610 ns per call on every family,
  with 329 words allocated: 6x to 9x the cost of a short search.
- **Engine cost, VM:** negative on jq (the VM is 32-40% faster than
  Oniguruma there: tiny subjects where Oniguruma's per-search set-up
  dominates); +85% / +50% (`ffi` / flambda) on PHP; +725% / +594% on VS
  Code, whose searches scan the rest of a line for literal or
  alternation patterns that mostly fail, where Oniguruma's search
  optimiser (Sunday/BMH, first-character map) skips positions the VM
  tries one by one.
- flambda `-O3` speeds the VM by 11-31%.
- `ocaml-re` (DFA, no backtracking, reference only) is fastest on PHP
  and close to C elsewhere, at the price of allocation.
