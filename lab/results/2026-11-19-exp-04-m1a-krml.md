# exp-04 m1a-krml: mechanism 1a, C from F* + Pulse through KaRaMeL

## What

Mechanism 1, emitter 1a, of experiment #4 (issue #7): one F* + Pulse
module, `OnigStub`, generated from the public headers (the whole
public API: 163 Pulse functions in the default build, 171 with POSIX,
30 encoding records with 16 function-typed fields each, 12 syntax
records, the case-fold flag), checked by F*, extracted with
`--codegen KrmlC` and KaRaMeL (`krml -no-prefix OnigStub`), compiled
with a hand-written C shell into `libonig.so.5` with CMake, and checked
for criteria 1-4. A construct probe (`Probe.fst`) was extracted first
to see the shape of the C. The same source and harness are used by 1b
([m1b-custard entry](2026-11-19-exp-04-m1b-custard.md)).

The plan scheduled mechanism 1 as follow-up 1; the bench host finished
milestone 1 early, so it ran in the same 3-hour window.

## Why

Stack C would produce libonig's C from F* + Pulse. The questions are
what the extracted C looks like at the ABI (names, struct layout,
static initialisers with function pointers) and which parts need a
hand-written C layer outside the proofs, per emitter (decision (b) on
the issue).

### Source and types

Every public function is a Pulse `fn` (`requires emp ensures emp`)
returning a fixed value; a pure F\* function returning `unit` was erased
by extraction (a first build lost the 23 `void` functions, e.g.
`onig_free`, `onig_region_free`), so all functions are Pulse functions.
C `int`/enums map to `Int32`, unsigned types to `UInt32`, `size_t` to
`SizeT`; every pointer (data or function) parameter or result is a
Pulse reference `ref UInt8` (extracted as `uint8_t *`, ABI-equivalent),
results are `Pulse.Lib.Reference.null`. The encoding record has the
fields of `OnigEncodingType` in order, function-typed fields with their
arities. `LowStar.Buffer` is not in this F\* release.

### What KaRaMeL emits (probe and full stub)

| Construct | KaRaMeL output |
|---|---|
| exported function | exact name with `-no-prefix OnigStub` (`int32_t onig_version_num(int32_t x)`) |
| record with function-typed fields | `typedef struct onig_encoding_type_s { int32_t (*mbc_enc_len)(uint8_t *x0); ... } onig_encoding_type;` |
| global record initialised with function pointers | **static initialiser**: `onig_encoding_type onigEncodingUTF8 = { .mbc_enc_len = s_mbc_enc_len, ... };` |
| exact mixed-case data name | **not possible**: F\* value names start with a lower-case letter, so `onigEncodingUTF8`; `rename_let` is ignored by KaRaMeL |
| pointer to another global (`OnigDefaultSyntax`) | not expressible (no address-of on a global in F\*) |
| variadic definition | not expressible (F\* has no C-variadic function type); a fixed-arity `custard_extern` declaration can call an external one |

### Hand-written C shell (outside the proofs)

- `krml_names.h`, force-included into the extracted C: 43 `#define

## Analysis

- **Binary drop-in: yes, at stub level, with a thin C shell**;
  **source drop-in: yes** (CMake, pkg-config, emscripten all pass on
  the extracted C).
- KaRaMeL keeps the ABI-critical layout: the generated structs have
  upstream's size, offsets and alignment, and globals holding function
  pointers get static initialisers, so the data is valid at load time.
- Outside the proofs, per criterion 5: the 43 data-symbol renames (a
  preprocessor layer, because F\* names cannot start with a capital and
  KaRaMeL ignores `rename_let`), `OnigDefaultSyntax`, the variadic
  `onig_error_code_to_str` (KaRaMeL cannot emit variadic definitions),
  and the build glue.
- The 16 extra exported symbols are the encoding callbacks, public F\*
  definitions in an entry module; making them `private` or bundling
  them would hide them. Not needed for the harness.
