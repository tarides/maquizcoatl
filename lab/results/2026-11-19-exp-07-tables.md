# Experiment #7, entry 3: the full table in each prover (criteria 1, 2 check, 3)

**What.** The whole of `upstream/src/unicode_property_data.c` (612 range
arrays, 24,443 ranges, the 629-entry `CodeRanges` index and the 886-name
lookup) loaded into Rocq, Lean 4, Why3 and F\*, with the time and memory
to check it (median of three clean runs) and the three fixed membership
queries evaluated inside each prover.

**Why.** First half of the question of experiment #7 (issue #11): can the
largest generated table of Oniguruma live inside the prover as
definitions it can compute with?

## Representations (criterion 1)

| Tool | Table | `CodeRanges` | Name lookup |
|------|-------|--------------|-------------|
| Rocq | one `Definition cr_X : list (Z * Z)` per array | `list (list (Z * Z))` of the 629 definitions, `nth` | `list (string * Z)`, linear search |
| Lean 4 | one `def cr_X : Array (UInt32 × UInt32)` literal per array | `Array (Array ...)` of the definitions | `Array (String × Nat)`, `find?` |
| Why3 | one `let constant cr_X : list (int, int)` per array (nested `Cons`) | a dispatch function `code_range (ct: int)` (629 `if`s); see below | `list (string, int)`, linear search |
| F\* | one `let cr_X : list (int & int)` per array | `list (list (int & int))`, `nth` | `list (string & int)`, linear search |
| F\* C targets | (a) `TableC.fst`: per array, a balanced decision tree over `U32.t`; (b) `PulseTable.fst`: per array, a Pulse static array (`Pulse.Lib.GlobalArray.mk_static_array`) of interleaved bounds, scanned linearly | (a) 629-way `if` chain; (b) balanced `if` tree on the ctype | none (names answered by the OCaml target) |
| Why3 C target | `tablec.mlw`: per array, a decision tree over `uint32` | 629-way `if` chain on `int32` | none (names answered by the OCaml target) |

The name lookup is the stated equivalent of criterion 1: the 886 names
(already normalised in the gperf pool) mapped to the 629 ctype indices.

**Result for criterion 1: every tool loads the full table, no failure,
no bisection needed.**

## In-prover membership queries (criterion 3)

Queries: `Lu` (ctype 146) at U+0041 (true) and U+00E9 (false);
`Grapheme_Base` (ctype 88), last range U+31350..U+323AF, at U+323AF
(true) and U+323B0 (false). Each query is its own file (one process),
timed once in timed run 1; Q0 is the same file with the import only, so
the cost of the query is the difference. All 20 answers (four
queries for each of the five evaluators) agree with the C oracle.

| Tool, evaluator | Q0 (import only) s | U+0041 Lu | U+00E9 Lu | U+323AF GB | U+323B0 GB | Query cost |
|-----------------|-------------------:|----------:|----------:|-----------:|-----------:|------------|
| Rocq `Eval vm_compute` | 0.82 | 0.83 | 0.84 | 0.84 | 0.83 | <= 0.02 s |
| Rocq `Eval native_compute` | 0.82 | 1.16 | 1.15 | 1.16 | 1.14 | about 0.33 s (includes on-demand native compilation) |
| Lean `#eval` | 0.36 | 0.45 | 0.46 | 0.45 | 0.45 | about 0.09 s |
| F\* `assert_norm` | 0.54 | 2.84 | 2.15 | 2.17 | 1.82 | 1.3-2.3 s |
| Why3 `why3 execute --rac-timelimit=1100` | see below | 116.85 | 119.06 | 112.99 | 134.67 | dominated by loading, see below |

- **Why3 `execute` costs about 2 minutes and 13.8 GB per query,
  independent of the query.** The baseline of timed run 1 (`why3 execute
  ... "0"`) failed to parse; an exploratory baseline, the cheapest real
  query `ctype_mem 0 10` (`NEWLINE`, one range), took 136.4 s and 13.8 GB
  ([raw/explore/why3-Q0b.b.log](2026-11-19-exp-07-raw/explore/why3-Q0b.b.log)),
  as much as the four fixed queries. The interpreter spends the time
  evaluating the module's globals (the 612 list constants), not the query.
  With the default RAC time limit the first query aborted with
  `FatalRACError(_, "RAC timelimit reached")`.
- **Why3 interpreter failure on nested constants.** With `CodeRanges` as
  a `let constant code_ranges : list (list (int, int))` built from the
  `cr_X` constants, every `why3 execute` on the module, even of
  `cr_X` alone, fails with `Type mismatch between list.List.list (int, int)
  and (int, int)`; reproduced on a 3-line module. Typing, VC generation and
  OCaml extraction accept it. Hence the dispatch-function representation.
- Lean `#reduce ctypeMem 146 0x41` fails with "maximum recursion depth
  has been reached"; with `set_option maxRecDepth 100000` it returns `true`
  in 0.61 s (Q0 0.36 s).

## Analysis

- All four provers take the whole table as ordinary definitions with no
  special encoding: Why3 types it in about 2 s, Rocq checks it in 25 s,
  F\* in 30 s, Lean elaborates it in 35 s, all under 1.6 GB.
- The representations that the C back ends need cost more to check:
  decision trees in F\* 41 s (1.4 GB); Pulse static arrays 163 s, the
  slowest check of the experiment, mostly in the 612 `assert_norm` on list
  lengths and the dispatch tree (one Pulse VC per branch).
- Computing with the table inside the prover is immediate in Rocq and
  Lean, seconds in F\*, and impractical in Why3's interpreter.
- Open: the effect of experiment #3's background load on absolute times is not
  measured; a rerun on an idle host would bound it.
