# exp-01 corpus: sources, pins, licences, pattern counts

## What

Static extraction of the regex patterns that Oniguruma's three main hosts
compile, from pinned sources: the `match`/`begin`/`end`/`while` strings of
VS Code's 83 `*.tmLanguage.json` grammars; the regex arguments of jq's
regex builtins in its tests and manual; the `mb_ereg*`/`mb_split` pattern
arguments in php-src's mbstring tests and the PHP manual. Each occurrence
becomes a (pattern, syntax, options, encoding) triple under the host's
compile configuration.

## Why

Criterion 1 of issue #5. The corpus is the input of the classification
(criteria 2-5) and of the workloads (criterion 6). Its scope follows
decision (a) on the issue: the hosts' own repositories only.

## Host compile configurations (confirmed in the pinned code)

| Host | Syntax | Options | Encoding | Evidence |
|---|---|---|---|---|
| VS Code | `ONIG_SYNTAX_DEFAULT` = Oniguruma | `CAPTURE_GROUP` | UTF-8 | vscode-oniguruma `src/onig.cc` `createOnigRegExp`; `src/index.ts` `OnigScanner` defaults `[FindOption.CaptureGroup]`, `Syntax.Default` |
| jq | `PERL_NG` | `CAPTURE_GROUP` + flags `i x m s p l n` | UTF-8 | jq `src/builtin.c` `f_match` |
| PHP | `RUBY` (option letters select others) | `MULTILINE\|SINGLELINE` by default | `mb_regex_encoding()`, default UTF-8 | php-src `ext/mbstring/php_mbregex.c` |

Divergences from the issue's Inputs section, none of which changes scope:

- vscode-textmate passes no syntax or options; the defaults come from
  vscode-oniguruma's `OnigScanner` (`CAPTURE_GROUP`, Oniguruma syntax), as
  the issue expected. `UseOnigurumaFindOptions` is `false`
  (`src/debug.ts`), so `\A`/`\G` are handled by rewriting them to U+FFFF in
  scanner variants, not by search-time options.
- PHP: an explicit option string *replaces* the default
  `MULTILINE|SINGLELINE` instead of adding to it; `mb_regex_set_options()`
  replaces the defaults for later calls. PHP also sets match limits
  (`mbstring.regex_retry_limit` 1,000,000, `mbstring.regex_stack_limit`
  100,000), different from upstream's defaults.
- vscode-oniguruma's repository HEAD declares version 2.1.0, which is not
  on npm (latest 2.0.1); VS Code pins 1.7.0, which the capture uses.

## Data

Occurrences (one per call site / grammar string) and distinct triples:

| Source | occurrences | literal | host-substituted | non-literal | distinct triples |
|---|---:|---:|---:|---:|---:|
| VS Code grammars (83 files, 82 with patterns) | 17,367 | 17,034 | 333 | 0 | 5,870 (compiled form) / 5,888 (grammar text) |
| jq (`tests/onig.test` 51, `manual.yml` 18; `jq.test` and `optional.test` have none) | 69 | 69 | 0 | 0 | 44 |
| PHP (php-src tests 142, manual 2) | 144 | 100 | 0 | 44 | 73 |

- *host-substituted*: `end`/`while` patterns with `\N` references to
  `begin` captures; the compiled form substitutes the empty string (the
  dynamic capture records the real substitutions).
- *non-literal*: PHP patterns built from variables or concatenation; they
  are counted, not compiled. Run-time capture recovers 131 such triples
  (workloads entry).
- PHP encodings found: UTF-8 (69 triples), EUC-JP (2), UTF-32BE (1),
  ISO-8859-1 (1).
- Patterns and occurrences are stored in
  `experiments/01-pattern-inventory/patterns/` (all licences permit
  redistribution); the 10 MB VS Code occurrence file is regenerated by
  `workloads/build.sh`.

## Analysis and open questions

- The jq and PHP corpora are small (44 and 73 triples) and test-oriented;
  this is the cost of decision (a). They exercise error paths: 7 of the
  73 PHP triples are deliberately invalid (bug-regression tests).
- VS Code dominates any pooled number (98% of triples); results are
  reported per source.
- The PHP lexer ignores control flow: `mb_regex_encoding()` calls apply to
  the calls that follow them in the text. Two occurrences follow a
  non-literal `mb_regex_encoding($enc)` and are marked
  `encoding_known: false`.
