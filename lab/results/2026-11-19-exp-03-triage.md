# exp-03 triage: one harness leak, no library bug; deep-pattern stack use

## What

Deduplication, minimisation and root-cause attribution of every artifact
of the [fuzzing campaign](2026-11-19-exp-03-fuzz-campaign.md), plus a
directed depth probe that answers decision 3 of issue #9 (stack
exhaustion within the default parse depth limit), since `fuzzer-deep`
itself never produced deep inputs.

## Why

Done-criteria 3 and 4 of issue #9. Decision 3 (maintainer, option (a)):
a stack exhaustion within the default depth limit (4096,
`upstream/src/regint.h:108`) is a confirmed bug and deviation-log
candidate only if it reproduces in the plain, non-sanitized build under
the default `ulimit -s`; ASan-only exhaustions are resource findings.

## Provenance

- Conditions of [provenance](2026-11-19-exp-03-provenance.md); host
  `ulimit -s` = 8192 KiB. Run 2026-11-19, 14:50-14:57 UTC, on the
  blocksci bench host, pinned to CPUs 8-31,40-63.
- Artifacts: `sh experiments/03-sanitizers-fuzzing/triage.sh` (replay
  with `read-regset`, `ASAN_OPTIONS=detect_leaks=1`), then
  `fuzzer-regset -minimize_crash=1 -runs=10000 -max_total_time=120`.
- Depth probe: `python3 -I experiments/03-sanitizers-fuzzing/deep-probe.py
  <hostdir>/harness <outdir>` (commit `e3091c6`): for 10 nesting shapes,
  bisect the largest nesting k that `read-deep-plain` accepts without a
  parse-depth error, then replay k and k+1 with `read-deep-plain` and
  the ASan + UBSan `read-deep`. Input format of `fuzzer-deep`: 8 control
  bytes (UTF-8, options 0, two-byte size, forward search), pattern, then
  a subject of 64 `a`.
- Deviation from the plan: `read-deep` aborts before parsing on a UBSan
  report in the harness itself (below), so the ASan replays were redone
  with `read-deep-ns`, identical except that the harness file is
  compiled with `-fno-sanitize=shift-base` (the library keeps the full
  `fuzz` build checks):
  `clang -I upstream/src -Wall -O1 -g -fno-omit-frame-pointer
  -fsanitize=fuzzer-no-link,address,undefined
  -fno-sanitize-recover=undefined -fno-sanitize=shift-base -DSTANDALONE
  harness/base-deep.c build/fuzz/libonig.a`.
- Stack need of the plain build: for each probe input at maximal
  accepted depth, bisect `ulimit -s` between 1024 and 8192 KiB (16 KiB
  resolution) on `read-deep-plain` (exit 139 = SIGSEGV).

## Raw data

### Artifact groups

| Group | Target | Artifacts | Kind | Top frames | Minimised reproducer | Root cause |
|---|---|---|---|---|---|---|
| G1 | `fuzzer-regset` | 6 (`leak-*`) | LeakSanitizer, 1,325 bytes in 4 allocations | `onig_new@regcomp.c:7746` ← `exec@regset.c:201` ← `LLVMFuzzerTestOneInput@regset.c:346` | [`regset-leak.min`](2026-11-19-exp-03-repro/regset-leak/regset-leak.min), 11 bytes `2e 00 3d 28 3f 4c 29 07 00 ff ff` (pattern `(?L)` after the control bytes) | **Harness**, `upstream/harnesses/regset.c:223-229` |

All 6 inputs contain the inline option `L` (`(?L`, `(?IL)`,
`(?PLLL…`). The parser turns it into `ONIG_OPTION_FIND_LONGEST` on the
regex (`upstream/src/regparse.c:7874-7876`), so `onig_regset_add`
rejects the regex with `ONIGERR_INVALID_ARGUMENT`
(`upstream/src/regexec.c:6259-6261`, as documented in
`upstream/doc/API:466-478`). The harness then frees the set and
returns, but never calls `onig_free(reg)` on the rejected regex
(`regset.c:223-229`): ownership stays with the caller on failure, so the
leak is the harness's. Replay output without leak detection prints
`ERROR: onig_regset_add(): 0` for all 6 (with leak detection, LSan exits
before stdout is flushed). Originals and the replay report:
[`repro/regset-leak/`](2026-11-19-exp-03-repro/regset-leak/),
[`raw/triage/`](2026-11-19-exp-03-raw/triage/).

No crash, timeout, oom, UBSan report or `exit(-2)` ("fuzz target
exited") artifact from any target; no internal-consistency error
(`ONIGERR_PARSER_BUG`, `STACK_BUG`, `UNDEFINED_BYTECODE`,
`UNEXPECTED_BYTECODE`) was observed.

### Harness UBSan report (not a library finding)

`upstream/harnesses/base.c:98` (`to_binary`, compiled only with
`-DSTANDALONE`): `mask = 1 << (sizeof(v) * 8 - 1);` is a signed
left shift of 1 by 31 (`runtime error: left shift of 1 by 31 places
cannot be represented in type 'int'`). Every `read-*` replay binary
built from `base.c` (and the `base-deep.c` copy) aborts there under
`-fno-sanitize-recover=undefined`. The libFuzzer targets do not compile
this function. Report:
[`raw/probe/read-deep-harness-ubsan.txt`](2026-11-19-exp-03-raw/probe/read-deep-harness-ubsan.txt).

## Analysis and open questions

- **No confirmed library bug from fuzzing.** G1 is a harness leak; the
  library behaves as documented. Nothing goes to the deviation log from
  the campaign.
- **Decision 3: no confirmed stack-exhaustion bug.** Within the default
  depth limit every shape runs in the plain build under the default 8
  MiB stack. The only exhaustion is `absent` at k = 2047 under ASan:
  a **resource finding**, not a deviation-log candidate. It is still
  close: the plain build needs about 5.6 MiB for it, 70% of the default
  stack, against about 1.4 MiB for the other shapes. A program that runs
  Oniguruma on a thread with a smaller stack (for example musl's 128 KiB
  default, or any `pthread_attr_setstacksize` below about 5.7 MiB) would
  crash on a 8 KiB pattern accepted by the default limit; the plain
  build crashes for every shape at 1 MiB. Spec note for Maquizcoatl:
  bound recursion by a stack budget (or make the passes iterative)
  rather than rely on a depth limit calibrated for 8 MiB.
- Mixed shapes (for example absent groups inside character classes and
  quantifiers) could use more stack per depth unit than any single
  shape; the probe tested pure shapes only. Follow-up: a probe over
  mixed shapes, and the fuzzer-deep follow-up of the campaign entry.
- Harness defects for the upstream harnesses (not Oniguruma library
  bugs): `regset.c:223-229` leak and `base.c:98` signed shift. Upstream
  is archived; they matter only for whoever reuses the harnesses.
