# exp-11 rebuild: a new bench directory for the re-runs

## What

All seven engine columns of experiment 11 rebuilt from the same pinned
sources as r1, in a new bench directory under the maintainer's own
account on the bench host. The dispatch probe and a short untimed check
of every column on the jq workload pass. Nothing was timed.

## Why

The r1 bench directory belongs to another account, so the r2-r4 re-runs
asked by the results review on issue #2 could not use it (see
`2026-11-19-exp-11-r1-corrections.md`). Decision of the maintainer on
2026-11-19: use a new directory under this account, at the default of
`env.sh` (`<bench>` below, `~/maquizcoatl-work/exp/11-perf-baselines`),
with every toolchain reinstalled there. The r1 directory was only read
(to compare the workloads and the check outputs), never written.

## Provenance

- Repository: branch `exp/11-perf-baselines` at `11c2545`, cloned by
  https into `<bench>/repo`, `upstream/` submodule at `f95747b`. This
  commit has the harness fixes made since r1: RE2 and Rust extract every
  capture group (`465850a`), ocaml-re computes groups in worst mode
  (`5aabc3e`), and `setup.sh` now installs the pinned mtime 2.2.0 and
  dune 3.25.0 (`11c2545`; r1 got the same versions unpinned).

  Ubuntu 24.04.5 LTS, Linux 6.8.0-100-generic). No root. 141 GB free
  after the rebuild, which takes 1.3 GB.
- Commands, each under `nice -n 10`, chained by a small runner under
  `nohup`:
  - `setup.sh` 15:13:52-15:18:16 UTC (4 min 24 s), exit 0;
  - `prepare_bench.sh f64aa5feb6c3246cc614be1d329adadbb636779a`

  Builds pinned with `taskset -c 16-19` (`BUILD_CPUS` of `env.sh`), at
  most 4 jobs, as in r1. Load average 0.3-1.9 during the rebuild.
- Run by Claude Code (Opus 5.5) in the experiment pipeline, 2026-11-19.

## Analysis and open questions

- Every column builds and passes the smoke test, so the bench directory
  is ready for the r2-r4 runs (`run.sh r2 all`, and so on). The binaries
  differ from r1's, as expected: the harnesses changed since r1.
- Caveat for the re-run note, on the worst case: the committed r1
  worst-case figures come from the older harnesses (ocaml-re with
  `Re.execp`, RE2 and Rust without group extraction), so in
  `2026-11-19-exp-11-worst-case.md` the automaton rows measure the
  overall match only. The r1 corrections note says ocaml-re "computed
  groups in r1, so its column is comparable"; that holds for throughput
  only.
