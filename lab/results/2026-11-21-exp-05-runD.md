# exp-05 runD: milestone 4 (Bedrock2, CN, RefinedC), refused by the disk floor; summary table

## What

Run D of the pipeline's take-back of experiment #5 (issue #13; plan
section "Taken back by the pipeline (2026-11-21)"): milestone 4
(Bedrock2, CN, RefinedC) on the prototype with the read accessor, then
the single summary table of milestones 1-4 on the issue.

Outcome: nothing was measured. The bench host had 19 GB free when the
run started, under the 20 GB floor, so `setup-pipeline.sh 4` refused
each install. It also refused an install of 0 GB. Nothing was deleted.
The run pinned the three tools in `pins.json` (commits, estimated disk
use) and added milestone 4 to `setup.sh` (a disk check then `vu_die`
per tool, as for milestone 3's last three tools) and to
`setup-pipeline.sh`. No prototype was written for the three tools,
since none could be checked. Bedrock2, CN and RefinedC stay
**pending**. They are not "deferred", since no install failed.

The summary table of all 14 rows was posted on issue #13 under
"Results", with each done-criterion checked. 7 rows have a verdict
(the report's six and hax's Rocq backend) and 7 are pending, so the
experiment is not done.

Raw outputs (redacted: `<shared-cache>`, `<exp>`; checked for the host
name, user names, home paths and other accounts' services before
commit) are in [`2026-11-21-exp-05-runD-raw/`](2026-11-21-exp-05-runD-raw/).

## Why

Milestone 4 is the last of the plan's four. Run D was also asked to post
the single table that the issue's done-criteria call for. The
disk-floor decision asked in the run A, B and C corrections (options
a-d) is still open. The run therefore applied the rule it was given:
before each install, stop when less than 20 GB would remain, report it
as a blocker, and delete nothing to make room.

## Analysis

- **Milestone 4 is blocked on the same decision as milestone 3.** Since
  19 GB is under the floor, no install of any size passes. The seven
  pending rows (hax F\*, hax Lean, Creusot, RefinedRust, Bedrock2, CN,
  RefinedC) need 35 GB by the current estimates, or 25 GB without hax
  Lean. Six of them also need their install written; only hax F\*
  (1 GB) is ready.
- **CN has moved.** The plan's tools table says "opam pin of a Cerberus
  checkout at master". Cerberus master now has only `cerberus*.opam`
  files and no `cn` package. CN is developed in `rems-project/cn`
  (pushed 2026-11-19, not archived), which uses `cerberus-lib`. Its
  install will be two pins. Both repositories are active, so the
  maintenance rule holds. Plan section "Deviations found during run D".
- **No prototypes.** CN and RefinedC would check C source shaped like
  VST's `vu.c`, with their annotations added. Bedrock2 would check its
  own source language, compiled to C. Annotations that no tool checks
  would show nothing about the done-criteria, and a link check of
  `vu.c` with GCC is already covered by VST's run. So none was written.
- **Summary table and conclusions** (also in the issue comment):
  - No stack A-F is eliminated. Each keeps a route that works or works
    with a shim: A VST, B Aeneas, C Pulse, D Verus, E Why3 C, F
    Isabelle-LLVM.
  - The Rust → hax → Rocq route is eliminated at hax v0.5.0, because
    the backend's output is ill-typed (not because of calls to
    unverified code).
  - Trusted-cost ranking among the six proven tools: Pulse 28 (works),
    VST 54 (works), Isabelle-LLVM 108, Verus 117, Aeneas 122, Why3 140.
    hax (126) is unranked, because nothing of it is proved.
  - The counts are not directly comparable (notes of `table.md`). The
    order still matches what each tool can express: only Pulse and VST
    call the pointer and take `vu_i_apply`'s address in verified code
    and lend the subject as a read-only share.
