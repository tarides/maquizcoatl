# exp-04 m2-c-stub: mechanism 2, C proven directly (hand-written C; Why3)

## What

Mechanism 2 of experiment #4 (issue #7): a C stub generated
mechanically from the public headers, built with CMake into a default
and a POSIX prefix, checked against the oracle
([oracle entry](2026-11-19-exp-04-oracle.md)) for criteria 1-3, then
the source-level criterion 4 (CMake, pkg-config, emscripten). Second
part: what Why3's WhyML-to-C extraction can emit at the ABI. The VST
front-end check (`clightgen`) is a separate entry.

## Why

Mechanism 2 has two routes with different ABI boundaries: for VST the
proof is about hand-written C, so the question is whether that C can be
a drop-in and whether the verifier's front end accepts it; for Why3 the
C is generated, so the question is which ABI constructs the generator
can emit and what must stay in a hand-written layer.

### The stub

`gen_c_stub.py` reads `gcc -aux-info` prototypes of `oniggnu.h` (which
includes `oniguruma.h`) and of `onigposix.h`, and emits one definition
per public function exported by the oracle (171 in the POSIX build, the
172nd, `onig_error_code_to_str`, is hand-written), each returning a
fixed value, plus the 44 public data symbols: 30 `OnigEncodingType`
file-scope initialisers holding 16 function pointers each (static
callbacks in `stub_data.h`), 12 `OnigSyntaxType` initialisers,
`OnigDefaultSyntax = &OnigSyntaxOniguruma`, `OnigDefaultCaseFoldFlag =
ONIGENC_CASE_FOLD_MIN`. `onig_error_code_to_str` is a C variadic
definition with `va_list`, reading the `OnigErrorInfo*` only for the 7
codes for which upstream does (`upstream/src/regerror.c:306-312`). The
POSIX file is compiled as upstream's `regposix.c` is (`regex_t` renamed
around `oniguruma.h`, `upstream/src/regposix.c:30-34`), because
`oniguruma.h` and `onigposix.h` cannot both be included otherwise. The
shipped headers are upstream's. No internal symbol is exported.

One module per construct (`m2-why3/abi.mlw`), `why3 extract -D c`:

| Construct | Result |
|---|---|
| (0) exported function, int32 arguments (`onig_version_num`) | extracted, exact name: `int32_t onig_version_num(int32_t x)` |
| (a) record with a function-typed field, value named `onigEncodingUTF8` | **not extracted**: `Could not translate declaration of 'enc'. Unsupported: arrow type`; the value: `Unsupported: partial application`. Both silently dropped from the C file (only the callback is emitted) |
| (a') record constant `onigSyntaxRuby` | extracted as a **function** `struct syn onigsyntaxruby()`, not as data, and the name is **lower-cased** |
| (b) declared global `val onigDefaultCaseFoldFlag : ref int32` | **not extracted**: `Unsupported: [C.translate_decl] Dval _`; uses refer to the lower-cased `onigdefaultcasefoldflag` |
| (b') defined global `let onigDefaultCaseFoldFlag = ref 1` | extracted as data `int32_t onigdefaultcasefoldflag = 1;`, name **lower-cased** |
| (c) variadic definition | not expressible: WhyML has no variadic functions |

## Analysis

- **Hand-written C (VST route): binary and source drop-in at stub
  level.** All public symbols, exact names and data sizes, SONAME,
  file names, every layout, every harness binary, pkg-config, CMake and
  emscripten pass. The only criterion 1 gap is the 114 leaked
  internals, which the stub deliberately does not export and which no
  harness binary needs. The C constructs at the ABI are ordinary C99:
  file-scope struct initialisers with function pointers, a `va_list`
  variadic. Whether VST's front end accepts them is the `clightgen`
  entry.
- **Why3 C extraction cannot produce the data half of the ABI.** WhyML
  value names must start with a lower-case letter, and the C printer
  then lower-cases the whole name (`onigSyntaxRuby` becomes
  `onigsyntaxruby`), so no mixed-case exported name can come out; it turns
  record constants into functions, rejects function-typed fields and
  `val` globals, and has no variadics. Function names in lower case
  (the whole `onig_*` API) come out exactly. So with Why3 the 44 data
  symbols, the encoding structs' function-pointer tables and
  `onig_error_code_to_str` sit in a hand-written C shell outside the
  proofs, calling extracted functions; the ABI boundary then looks like
  mechanism 1's (generated C plus a hand-written shell).
- Unsupported declarations are dropped with a message on stderr and a
  zero exit status: a build relying on Why3 extraction must check the
  log, not the exit code.
