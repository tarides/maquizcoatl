# exp-05 runA: pipeline toolchains and replay of milestones 1 and 2

## What

Run A of the pipeline's take-back of experiment #5 (issue #13; plan
section "Taken back by the pipeline (2026-11-21)"). The milestone 1 and
2 toolchains are installed into the project's shared toolchain cache on
the bench host with the pins of `pins.json`, through the new
`setup-pipeline.sh`, which runs @balat's `setup.sh` unchanged. Then the
six prototypes of milestones 1 and 2 (Why3, F\* + Pulse, Verus,
Charon + Aeneas, VST + CompCert, Isabelle-LLVM) are replayed from the
branch with these toolchains: build and proofs, link with the C caller,
output against `caller/expected.txt` (which covers both re-entrancy
shapes), negative control, and `count-trusted.sh`. Each result is
compared with the recorded raw outputs of the
[`review-fixes`](2026-11-20-exp-05-review-fixes.md) entry. Raw outputs,
redacted by the scripts, are in
[`2026-11-21-exp-05-runA-raw/`](2026-11-21-exp-05-runA-raw/).

## Why

The earlier runs used a toolchain cache that the pipeline's account
cannot read. Before runs B to D change the prototype (read accessor,
Isabelle-LLVM composition) or add tools, the pipeline needs its own
toolchains and evidence that they reproduce the recorded milestone 1-2
results; otherwise a later difference could not be told apart from a
toolchain difference.

### Differences from `setup.sh`'s own layout

`setup-pipeline.sh` lists them in its header; it never runs a
`setup.sh` step that would rewrite something already in the shared
cache.

- F\* and Verus are the shared cache's copies, at `<shared-cache>/fstar`
  and `<shared-cache>/verus` rather than `<cache>/fstar/<version>` and
  `<cache>/verus/<version>`; the view links `fstar/current` and
  `verus/current` to them, and the `fstar` and `verus` steps are not
  run (their `find` does not descend into a linked start directory).
  `setup-pipeline.sh check` verifies the sha256 of both downloads
  against `pins.json` and the version strings.
- LLVM and Isabelle were installed by experiment #4 with the same pins;
  the `llvm` step is not run, since it would re-point the shared
  `llvm/current` link. The `isabelle-llvm` step runs and finds every
  part present.
- opam, rustup, cargo and elan are the shared ones: the switch `vst` is
  added to the shared opam root (the switches `provers`, `compcert`,
  `ffi` and `ffi-flambda` are untouched), the Rust nightly and Lean
  rc2 are added to the shared rustup and elan. The shared elan is 4.4.0
  as pinned.
- The view has its own `why3/why3.conf` and `env.sh`; the shared
  cache's are untouched. Mathlib's download cache and `XDG_CACHE_HOME`
  are inside the shared cache, not the account's home.
- jq 1.8.2 (pinned in `lib.sh`) was installed into `<shared-cache>/bin`:
  the host has no jq.

### Comparison with the recorded raw outputs

`result.txt` is identical for every normal run and every control, apart
from the run id, the CPU set and the build time. In `build.log`, after
masking timings, the only differences are:

- **Verus: `libvu.a` has another sha256** (same size, 24,479,232
  bytes). Not a toolchain difference: two of our own builds from the
  same commit (`runA-m1` and a scratch run `runA-det`, not recorded
  further) also differ. The library embeds the build path of `lib.rs`,
  which contains the run id. The Aeneas `libvu.a`, built by rustc from
  a path that also contains the run id, is byte-identical to the
  recorded one, so the cause in Verus's case is not established beyond
  that; it does not affect the proof or the caller's output.
- **Why3: one more prover in the configuration.** The view's
  `why3.conf` was generated with Isabelle on `PATH`, so `why3 config
  list-provers` also prints "Isabelle 2026". The proofs use only
  Alt-Ergo and Z3. In the control, the step counts at timeout differ
  slightly (Alt-Ergo 309,159 against 307,760; Z3 24,221,770 against
  24,232,016), as expected from a time limit.
- **Pulse:** the path of `krml` (the shared copy) and one rounded timer.
- **Isabelle-LLVM:** no "Cleaned VU" line (no earlier `VU` session in
  this heap directory), and the control log prints the failing goal
  once more, in the theory's own error message, before the build
  summary; the goal is the same.
- VST: none, for the normal run and the control.

## Deviations

- `setup.sh`'s `base` step failed (status 1) in one of the two
  parallel milestone 2 runs: both wrote `<cache>/env.sh.new` at the
  same moment and one `mv` found it gone. The file written is the same
  for both runs, the other steps ran, and the next run rewrote it; that
  run's `SETUP-END` is status 1 for this reason only.
- `vu_du` prints 0 or 32K for the cache in the setup logs, because
  `<cache>` is a directory of links; the disk figures above come from
  `du` on `<shared-cache>`.
- `provenance.txt`: the `lean` line fails as in the recorded run (no
  elan default; Lean comes from the Aeneas library's `lean-toolchain`).

## Verdict

All six prototypes reproduce with the pipeline's toolchains: every normal run is proven, links with the C caller and prints exactly `expected.txt` (both re-entrancy shapes included), every negative control is rejected on the same goal as recorded, and the trusted-line counts are unchanged (128, 25, 102, 109, 44, 100). The differences found are in build artefacts and logs only (Verus `libvu.a` hash, Why3's prover list), none in a proof or an output.

The verdicts of milestones 1 and 2 are unchanged. Runs B to D can use
these toolchains.
