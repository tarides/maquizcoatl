# exp-05 harness: prototype interface, C caller and branch rules

## What

The shared harness of experiment #5 (issue #13), written before any
tool runs: the C interface every prototype implements
(`experiments/05-unverified-calls/proto.h`), the C client that supplies
the function pointers (`caller/caller.c`), its expected output
(`caller/expected.txt`), an unverified pure-C reference of the verified
functions (`caller/reference.c`), and the scripts of the plan
(`setup.sh`, `run.sh`, `count-trusted.sh`, `provenance.sh`, with
`lib.sh` for their shared helpers, and `pins.json`). Approach steps 1
and 4 of `plans/05-unverified-calls.md`.

## Why

The prototypes of every tool are compared against one caller and one
expected output, so that "the caller's output equals `expected.txt`"
means the same thing for each tool. The branch rules that
`vu_callout_step` must prove are re-read from `regexec.c` here, once,
with citations, so that no prototype has to rely on the plan's summary.

## Branch rules at `f95747b`

All references are to `upstream/` at `f95747b`. `USE_CALLOUT`
(`upstream/src/regint.h:76`) and `USE_FIND_LONGEST_SEARCH_ALL_OF_RANGE`
(`upstream/src/regint.h:102`) are defined in the default build. The
return values are `ONIG_CALLOUT_FAIL = 1` and
`ONIG_CALLOUT_SUCCESS = 0` (`upstream/src/oniguruma.h:774-777`); the
comment above them says "less than -1: error code"
(`upstream/src/oniguruma.h:773`).

**Progress direction** (`upstream/src/regexec.c:4615-4632`). The callout
is called through `CALLOUT_BODY` (`upstream/src/regexec.c:1180-1197`,
which fills an `OnigCalloutArgs` on the stack and calls
`(func)(&args, user)`), then:

- `ONIG_CALLOUT_FAIL`: `goto fail`, i.e. backtrack (`:4619-4621`);
- `ONIG_CALLOUT_SUCCESS`: `goto retraction_callout2` (`:4622-4624`),
  which pushes a retraction callout on the backtrack stack when the
  callout is registered for the retraction direction (`:4635-4648`),
  then matching continues;
- any other value (`default`, `:4625-4631`): a positive value is replaced
  by `ONIGERR_INVALID_ARGUMENT` (-30), and the value is stored in
  `best_len` and returned from `match_at` (`goto match_at_end`).

**Retraction direction** (`RETRACTION_CALLOUT`,
`upstream/src/regexec.c:1218-1234`), run when the backtrack stack is
popped through a callout entry (`POP_CALLOUT_CASE`,
`upstream/src/regexec.c:2287-2291`):

- `ONIG_CALLOUT_FAIL` and `ONIG_CALLOUT_SUCCESS`: `break`, the pop
  goes on (there is nothing left to backtrack);
- any other value: positive becomes `ONIGERR_INVALID_ARGUMENT`, and the
  value is returned from `match_at` (`best_len = result; goto
  match_at_end`).

**Each-match callback** (`upstream/src/regexec.c:3387-3400`), called at
each match when `ONIG_OPTION_CALLBACK_EACH_MATCH` is set and a callback
is registered:

- negative: returned from `match_at` as an error
  (`MATCH_AT_ERROR_RETURN(i)`, `:3391-3394`);
- any other value: `best_len = ONIG_MISMATCH` (`:3395-3398`), then
  `goto fail`, so the search goes on. Under `ONIG_OPTION_FIND_LONGEST`
  `best_len` is not reset (`:3395-3397`), so the longest match found so
  far is kept. The prototype models the default (no `FIND_LONGEST`)
  case.

**What a negative value does next.** `match_at` returns the negative
value; the search loop's `MATCH_AND_RETURN_CHECK`
(`upstream/src/regexec.c:5720-5727`) treats `ONIG_MISMATCH` (-1) as "no
match at this start position" and moves on to the next one, and ends
the search with any other negative value as an error. So a callout or
callback returning -1 does not abort the search, unlike -2 and below;
this is consistent with the header comment ("less than -1: error
code"). The prototype's `vu_callout_step` stops at the `match_at` level:
it returns every negative value unchanged, and the distinction is the
outer loop's. `caller/expected.txt` labels -1 `mismatch` and the
other negative values `error` accordingly.

**How the prototype encodes it.** `vu_callout_step(dir, f, args, ud)`
returns `VU_ACT_CONTINUE` (0), `VU_ACT_BACKTRACK` (1), or a negative
error code:

| `dir` | callee 0 | callee 1 | callee > 1 | callee < 0 |
|---|---|---|---|---|
| progress | continue | backtrack | -30 | callee |
| retraction | continue | continue | -30 | callee |
| each-match | backtrack | backtrack | backtrack | callee |
| other | -30, callee not called | | | |

## Accessors

`onig_get_callout_data` (`upstream/src/regexec.c:1828-1848`) and
`onig_set_callout_data` (`upstream/src/regexec.c:1881-1896`), behind the
`_by_callout_args` accessors (`upstream/src/regexec.c:1864-1871` and
`:1912-1919`), reject `callout_num <= 0` with `ONIGERR_INVALID_ARGUMENT`
but check neither `slot` against `ONIG_CALLOUT_DATA_SLOT_NUM` (5,
`upstream/src/regexec.c:177-183`) nor `callout_num` against the number
of callouts the match parameter was sized for
(`upstream/src/regexec.c:1746-1759`). A client callout passing
`slot = 5`, a negative slot or a too large `callout_num` reads or writes
outside `mp->callout_data`. The prototype's `vu_get_slot` and
`vu_set_slot` check `0 <= k < 5` and return `ONIGERR_INVALID_ARGUMENT`
otherwise (the caller probes 5, -1 and `INT_MIN`). This is a deviation
candidate for the spec (bounds-checked accessors); it is not filed yet.

## Caller

`caller/caller.c` prints one line per check (53 lines), then a final
`failures=N` (the caller's own checks: bounds unchanged, result in
bounds, verified-side state unchanged, record within capacity). It
supplies:

- encodings: upstream's UTF-8 `mbc_enc_len` (`upstream/src/utf8.c:47-74`,
  with only the `USE_RFC3629_RANGE` arm since `:33` defines it, notice
  kept), bounds [1, 4]; experiment #4's client encoding
  (`c_mbc_enc_len` of `experiments/04-abi-feasibility/client_encoding.c`
  on branch `exp/04-abi-feasibility`, single byte), bounds [1, 1]; a
  misbehaving one returning 0, -5, 100, `INT_MIN` and `INT_MAX`, with
  bounds [1, 4] and [2, 3];
- callouts returning 0, 1, 2, -1, -2, `INT_MAX` and `INT_MIN` in the
  three directions, plus two invalid directions (3 and -1);
- re-entrancy (b): a callout calling `vu_get_slot` and `vu_set_slot` by
  name (read slot 0, write slot 0 + 1 into slots 0 and 4, three
  out-of-bounds probes), in both directions, plus one direct call of the
  accessors;
- re-entrancy (a): an `apply_all_case_fold` walking a 13-entry table and
  calling back `vu_i_apply` through the pointer it receives, with
  `to_len` values 0 to 4 and -1, more in-range entries than the record
  holds (8), a counter start near `INT_MAX` (saturation), and a client
  that stops early with its own result (-7).

Deviation from the plan: the plan says the encoding part is taken from
experiment #4's `client_encoding.c` instead of upstream's UTF-8 when
experiment #4 has published it. It has, but its encoding is single-byte
(`mbc_enc_len` always 1, bounds [1, 1]), which leaves the clamp nothing
to do on a well-behaved callee. The caller therefore uses both:
experiment #4's function (copied, not rewritten, with its call counter)
and upstream's UTF-8 one for the multi-byte case.

## Caller check (approach step 4)

On the workstation, caller and reference built with
`cc -std=c11 -Wall -Wextra -Wpedantic -Werror
-fsanitize=address,undefined -fno-sanitize-recover=all`: output equal to
`caller/expected.txt`, `failures=0`, exit 0, no sanitizer report. Then
through the harness, `run.sh reference local-check` with `VU_EXP` set to a
scratch directory:
`caller_output=same`, `caller_status=0`.

The harness scripts were also exercised on a throw-away tool directory
(not committed):

- a `build.sh` whose library drops the upper clamp gives
  `caller_output=DIFFERENT` with the out-of-range lines in `caller.diff`;
- `run.sh -n` is refused until a normal run of the same tool and run id
  has passed; then a `build.sh` exiting with `VU_PROOF_REJECTED` (3)
  gives `control=rejected`, one exiting with another failure status
  gives `control=error`, and one that succeeds gives `control=ACCEPTED`;
  only `rejected` exits 0;
- `VU_CPUS` is required for every tool but the reference; `4-5` is
  refused (reserved CPUs), as are a malformed list (`8-`), an offline
  CPU, and a CPU pinned by an unrelated process, while running the
  script itself under `taskset` (or from a pinned shell) is accepted;
- a reused run id, a non-numeric `VU_JOBS` and a non-numeric
  `VU_VMEM_KB` are refused before anything is written;
- `count-trusted.sh` counts C block, line and trailing comments, and F\*
  `//` and nested `(* *)` comments, correctly, and refuses the ranges
  `5-`, `-2`, `5-1`, `0-2` and a range past the end of the file;
- `provenance.sh` refuses a bad phase before writing anything, records
  a dirty tree as `<commit>-dirty`, and records `upstream/` both as the
  gitlink and as the checked-out commit (`not-initialised` in a fresh
  clone), compared with `pins.json`;
- `vu_fetch` with no pinned sha256 records the first download's hash
  next to it and refuses a later file that differs;
- the caller detects a `vu_get_slot` that writes its output on the
  out-of-bounds path (6 `FAILED` lines with a mutated reference).

`expected.txt` was produced by the reference and then checked line by
line against the rules above and the UTF-8 table.

## Deviations from the plan (decided on issue #13 before this run)

- **Toolchain cache.** Experiment #7's cache on the bench host belongs
  to another account: it is readable but not writable from the account
  that runs this experiment. Its tools are used read only where they
  work (F\* with `krml` and Z3, elan and Lean, the opam switch `provers`
  with Why3 and Alt-Ergo); in the scripts it is `VU_SHARED_CACHE`,
  redacted as `<shared-cache>`. Everything installed or written (Rust
  toolchains, Verus, Charon and Aeneas, elan and Aeneas's Lean, the VST
  opam root and switch, Isabelle, the AFP and Isabelle-LLVM, the Why3
  configuration with its Z3 registration) goes into this account's own
  cache, `<cache>` (`VU_CACHE`, same layout and `env.sh`), and the
  experiment directory `<exp>` (`VU_EXP`). The VST switch therefore
  lives in a separate opam root, not in experiment #7's.
- **Jobs and CPUs.** Up to 12 jobs for the VST, Isabelle-LLVM and
  RefinedRust installs, 4 otherwise (`vu_jobs` in `lib.sh`). Every
  heavy job runs under `nice` and is pinned with `taskset` to free
  CPUs (`VU_CPUS`), never 4-7 or 36-39 (experiment #11) nor a CPU that
  another process pins; `vu_check_cpus` checks this before each job.
  `run.sh` (except for the reference) and `setup.sh` refuse to start
  without `VU_CPUS`; `setup.sh` pins and renices itself, so every
  command it runs inherits the CPU set.
  The plan said no pinning was needed.
- **Isabelle-LLVM** is shared with experiment #4's mechanism 4, which
  must run alone on the bench host: `setup.sh 2 isabelle-llvm` refuses
  to run unless `VU_ISABELLE_LLVM_OK=1` (set once issue #7 says the
  mechanism is not running) and no Isabelle or Poly/ML process is
  running.
- **Interim verdicts.** A toolchain that cannot be installed gives
  "deferred"; an install that does not finish in time gives "pending".
- **hax backends:** F\*, Rocq and Lean (milestone 3).
- **Disk:** about 100 GB free on the bench host (the plan said 142 GB);
  use is recorded per tool (`setup.sh` writes `disk.txt`).

## Download pins

The AFP is pinned to the dated release `afp-2026-11-19` with its
sha256, rather than `afp-current`, which changes daily (the 2026-11-19
file is the same size as `afp-current` that day, and contains the
sessions Isabelle-LLVM needs). The Isabelle2026 tarball has no
published checksum and its mirror was unreachable from the workstation:
`setup.sh` records the sha256 of the first download in `<cache>` and
checks later uses against it; the value goes into `pins.json` and the
notebook when milestone 2 runs.
