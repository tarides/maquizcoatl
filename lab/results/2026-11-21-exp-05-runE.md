  list, and `setup.sh` writes `env.sh` through a file of its own

- **CN** and **RefinedC**, first tries: `opam pin add` of the checkouts

  (`--filter=blob:none`). The pins use `--kind=path`. RefinedC's second
  try failed at `dune subst` ("repository does not contain any version
  information": a path pin has no `.git`); `refinedc` and `coq-lithium`
  are now pinned by URL at the commit, as RefinedC's README does.
  Before that fix, `coq-lithium` had been installed from the `iris-dev`

### hax, F\* backend (`hax-fstar/`)

With F\* v2025.10.06, the first check failed at the first call of a
client method (`Vu.fst`, F\* error 19, "Assertion failed"): hax gives a
trait method without `requires` an abstract F\* precondition
(`f_enc_len_pre`), which no caller can establish. This is what run C
predicted from reading `Vu.fst`. `EncLen` and `Callout` now carry
`#[hax_lib::requires(true)]`. That obliges each implementation to
accept every argument; the implementations are in `ffi.rs`, which hax
does not extract, so the two trait declarations are counted as client
contracts (8 lines). Trusted lines: shims 30, C glue 91, client
contracts 13, **134** (`trusted.tsv` of `runE-c`).

`runE` and `runE-c`: all modules checked (F\* `status Vu.fst: 0`),
caller output equal to `expected.txt`, 99 s. Clamp control: error 19,
"Could not prove post-condition" at `char_len`'s ensures. Read control:
error 19, "Subtyping check failed" at the slice index of
`get_subject_byte`. `build.sh` now names F\*'s cache directory for
both version formats ("F\* 2025.10.06" and "F\* version: ..."); in the
first try the name was empty. **Verdict: works with trusted shim.**

### Creusot (`creusot/`)

The prototype is Aeneas's design (`src/lib.rs` with Creusot contracts;
`src/ffi.rs` is Aeneas's glue, `cfg(not(creusot))`): one trait per
client function, the verified functions generic over them. `callout_step`
returns `(action, raw)` as hax's does, and the glue drops `raw`.
`EncLen` and `Callout` have no contract: Creusot treats a method
without contract as a relation (any result, possibly a different one at
each call), so nothing is assumed of the callee, not even determinism.
`ApplyAll`'s contract (the record invariant) is the client contract of
shape (a), trusted. `Apply`'s contract is refined by `IApply`, which
Creusot checks (`apply__refines`).

`cargo creusot` translates 9 Coma files and Why3find proves all of them
(`Proved (9 files)`), 46 s with the build. Clamp control: "proof
failed", goal `vc_char_len` (1 of 2 proved). Read control: goal
`vc_get_subject_byte` (3 of 4). The build copies `why3find.json` from
Creusot's data directory, as `cargo creusot init` does. Miri (Stacked
and Tree Borrows) accepts `client.rs` against Creusot's sources.
Trusted: shims 30, C glue 88, client contract 5, **123**.
**Verdict: works with trusted shim.**

### CN (`cn/`)

CN cannot call a client pointer: on a probe it reports "Function pointer
must be provably equal to a defined function" at the call. The three
indirect calls are in C shims marked `trusted` (CN takes their
specifications and does not check their bodies), as for Isabelle-LLVM;
`vu_i_apply`'s address is taken in the apply-all shim. Their
specifications are the callee contracts: the encoding function is lent
nothing; the callout gets `RW<struct vu_args>` and gives back some
`vu_args` (the verified side restores its fields); the apply-all
function keeps `rec_wf`. CN has no read-only share: the read accessor
takes the subject whole (`each ... RW<unsigned char>`) and its
postcondition says the same bytes come back. CN's specification of
`vu_callout_step` cannot name the callee's result: it says the result
is 0, 1, or negative (-30 for an invalid `dir`), and the exact rule is
`vu_rule`'s specification.

In this CN version, C integers are mathematical integers in
specifications (`1i32 <= lo` is a type error), and an array read
needs `focus` and `instantiate`. `cn verify`: 8 functions pass, 1 s.
Clamp control: "Unprovable constraint" at `return r` against the
postcondition. Read control: "Pointer `A.subject` needs allocation ID"
(`UB_CERB004_unspecified__pointer_add`) at `s[i]`: CN rejects the
out-of-bounds pointer arithmetic itself. `count-trusted.sh` counts a
`/*@ ... @*/` block as code. Trusted: the shims with their
specifications 19, `rec_wf` 3, **22**. **Verdict: works with trusted
shim.**

### RefinedC (`refinedc/`)

RefinedC calls the client pointers from verified code. Each pointer
argument has a `function_ptr` type that carries the callee's
specification, and `vu_fold_all` passes `vu_i_apply` with its proven
specification to the client: shape (a) is in verified code, as for
Pulse and VST. The subject is a shared, read-only array (`&shr`) held
by `vu_args`, so neither the callout nor the accessor can write it;
RefinedC's `&frac<q, ...>` takes `q : own_state` (owned or shared),
not a fraction. RefinedC reads struct refinements from attributes in
the struct definition, so `vu_rc.h` is `proto.h` with `[[rc::...]]`
attributes, which `build.sh` checks against `proto.h`.

`refinedc check` proves the seven functions; `Print Assumptions` of
each proof: "Closed under the global context". The C tests are written
`y <= x` rather than `x >= y`: the failed branch of `x >= y` reaches
the automation as `(x ?= y) = Lt`, which `lia` does not read.
`vu_callout_step`'s postcondition "∃ r, result = rule dir r" needs a
witness tactic (`solve_rule`: the result itself, or 0, 1, 2). 78 s.
Clamp control: "Cannot solve side condition in function
`vu_char_len`". Read control: "Cannot solve side condition in function
`vu_get_subject_byte`" at the read. Trusted: callee contracts 12, the
refinement types of `vu_args` and `vu_fold_rec` they use 12, `rec_wf`
1, **25**. **Verdict: works.**

### Bedrock2

Installed (coqutil and bedrock2's `noex` target built with Rocq
9.3.0), no prototype written within the cap. From the sources: the
language calls functions by name (`cmd.call`) and external code

## Analysis

- Two C verifiers join VST: RefinedC verifies the indirect calls
  itself, with the callee's specification in the pointer's type, and
  hands the client a verified function with its proven specification
  (25 trusted lines). CN cannot call a pointer that is not provably a
  known function, so it needs shims (22 lines). Both modelling styles
  of the earlier tools reappear: RefinedC is a client-contract tool
  like Pulse and VST, CN a shim tool like Isabelle-LLVM.
- The three Rust tools with a verdict (hax F\*, Creusot, and earlier
  Verus and Aeneas) all need the trait-plus-glue design and carry
  117-134 trusted lines, most of it the C glue.
- Read access: RefinedC expresses the read-only subject directly
  (`&shr`), like Pulse and VST; CN cannot (no fractional or shared
  permission), like Isabelle-LLVM; Creusot and hax read a shared slice
  made by trusted glue, like Verus and Aeneas.
- hax F\*: a trait method needs an explicit `requires(true)` to be
  callable, which turns into an obligation on the C client.
