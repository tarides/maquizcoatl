# exp-05 runC: milestone 3 (hax, Creusot, RefinedRust), stopped by the disk floor

## What

Run C of the pipeline's take-back of experiment #5 (issue #13; plan
section "Taken back by the pipeline (2026-11-21)"): milestone 3, on the
prototype extended with the read accessor in run B. In scope: hax with
three backends (F\*, Rocq, Lean), each with its own verdict, Creusot
and RefinedRust, plus the Miri test of shape (b) where it applies.

Outcome in one paragraph: hax's full toolchain (cargo-hax v0.5.0, its
OCaml engine and its Rust nightly) was installed, and a hax prototype
written, with the read accessor and the same design as Aeneas's. It
extracts to F\* and to Rocq, links with `caller.c` (output equal to
`expected.txt`) and runs clean under Miri (Stacked and Tree Borrows).
No proof could be checked:

- **hax, F\* backend: pending.** The F\* of the cache (2026.11.15)
  cannot read hax's output (`FStar.Mul` no longer exists, error 134).
  The F\* that hax pins (v2025.10.06, about 1 GB) was refused by the
  20 GB disk floor.
- **hax, Rocq backend: does not work at v0.5.0.** The emitted model
  does not type-check with Rocq 9.3 against hax's own Rocq library at
  the same tag. A one-field struct fails (`t_S` is referenced, but the
  record is defined as `S_record`), and so does one comparison (`f_lt`,
  which the library names `PartialOrd_f_lt`). The `ensures` clauses
  become lemmas ending in `Admitted`.
- **hax, Lean backend; Creusot; RefinedRust: pending.** Their installs
  (estimates 10, 7 and 6 GB) were refused by the disk floor.

Raw outputs (redacted by `lib.sh`; checked for the host name, user
names, home paths and other accounts' services before commit) are in
[`2026-11-21-exp-05-runC-raw/`](2026-11-21-exp-05-runC-raw/).

## Why

Milestone 3 gives verdicts for the next three tools on a stack A-F
route (Decision 1 of the plan). The disk-floor question asked in the
run A and run B corrections (options a-d) has not been answered yet.
This run applied the rule it was given: before each install, stop when
less than 20 GB would remain, and report it as a blocker. It used no
deletion to make room.

### The hax prototype (`hax/`)

`src/lib.rs` is Aeneas's `lib.rs` (run B) with hax-lib specifications
(`requires`, `ensures`, `future(..)` for `&mut` arguments). It differs
from Aeneas's in four ways:

- Pointers that the verified side passes through without reading (the
  encoding's byte pointer, `vu_args.subject`) are `usize` addresses.
  hax has no raw pointer type. The glue exposes the addresses and
  rebuilds pointers from them (`expose_provenance`,
  `with_exposed_provenance`).
- `callout_step` returns `(action, raw)`. The postcondition is
  `action == rule(dir, raw)` for a valid `dir`, and the verified-side
  fields of `args` are unchanged. The glue drops `raw` (a ghost value,
  as in Verus).
- `Apply` and `ApplyAll` carry contracts on their method: the record
  invariant `rec_wf` is preserved. `IApply`'s instance must prove its
  contract from `i_apply`'s. `ApplyAll`'s contract is the client
  contract of shape (a): it is trusted, since its only implementation
  is in `ffi.rs`.
- `get_subject_byte` requires `subject.len() == subject_len`, as
  Verus's does.

`src/ffi.rs` is Aeneas's `ffi.rs`, adapted. `TRUSTED`: shims 30
lines, C glue 91 lines, client contract 5 lines (`lib.rs:105-109`),
126 in all (`trusted.tsv`).

### hax, F\* backend (`hax-fstar/`)

`result.txt`: `build_status=1`, `verdict=build-failed`, 7 s. hax
extracted `Vu.fst` (388 lines, sha256 `0f5cc85b…`, committed in
`extracted/`) with no escape (`admit`, `assume`, `sorry`, …). F\*
2026.11.15 stops at line 3:

```
* Error 134 at Vu.fst(3,11-3,14):
  - Namespace ‘FStar.Mul’ cannot be found.
```

F\* 2026.11.15 also refuses hax's `--cmi` flag as unrecognised;
`build.sh` drops the flag when F\*'s `--help` does not list it. The
plan's fallback, the F\* hax pins (v2025.10.06), is the install the
disk floor refused. **Verdict: pending.**

Two things can be read from `Vu.fst` without running F\*. They are
expectations for the next run, not results:

- A trait method without a contract (`EncLen::enc_len`,
  `Callout::callout`) becomes a type-class field with an abstract
  `f_enc_len_pre`. A generic caller such as `char_len` may then have to
  prove that abstract precondition, which needs an explicit
  `requires(true)` on the trait. That would make the callee
  specification a client contract (each instance proves its
  precondition is true) rather than no assumption at all.
- `ApplyAll`'s contract becomes refinements on the instance's `pre` and
  `post` fields (`rec_wf v_rec ==> pred`, `pred ==> rec_wf
  rec_future`): an obligation on each instance, discharged by none,
  since the C client's instance is not extracted.

### hax, Rocq backend (`hax-rocq/`)

`result.txt`: `build_status=1`, `verdict=build-failed`, 31 s
(building the two libraries included). hax extracted `Vu.v` (329
lines, sha256 `228b1d76…`, committed). `RecordUpdate` and `Core` build
with Rocq 9.3. The model fails at its first use of a struct type:

```
File "./Vu.v", line 92, characters 25-36:
Error: The reference t_VuFoldRec was not found in the current environment.
```

The extraction has further defects that Rocq never reaches, since it
stops at the first error. Each one can be read in `extracted/Vu.v`:

- records are defined as `VuFoldRec_record` with fields
  `VuFoldRec_f_calls`, but used as `t_VuFoldRec` and `f_calls`;
- record updates are written `t_VuFoldRecf_calls` (no separator);
- `(fstres)` is written for `(fst res)`;
- the instance of `t_Apply` sets a field `implaabbcc_t_Apply_f_apply`
  that the class does not have;
- the contracts of `Apply` and `ApplyAll` are dropped from the classes;
- `fold_all` calls `f_apply_all` without its type argument `IApply`.

Every `ensures` becomes a lemma `…_ensures` ending in `Proof.
Admitted.`: 7 in all. They would have to be proved by hand, as with
Aeneas.

The probes (`hax-rocq/probes/`, `rocq-probes.log`) separate the backend
from the prototype:

- `struct` (a one-field struct, a getter and a setter, no
  specification) fails the same way: `The reference t_S was not found`.
- `cmp` (`add1` with `requires(x < 100)`, `setup.sh`'s smoke crate)
  fails with `Unbound and ungeneralizable variable f_lt`. The tag's
  `Core` library names that method `PartialOrd_f_lt`
  (`src/Core_Cmp.v:165`).

So at cargo-hax v0.5.0 the Rocq backend's output does not type-check
against the library shipped at the same tag, for code smaller than the
prototype. **Verdict: does not work**, for this reason. Experiment #1's
numbers go next to it, as the plan asks: 0 callouts and UTF-8 only
across its 5,870 triples. This failure has nothing to do with calls to
unverified code: the backend cannot model a struct or a comparison. It
is not a toolchain install problem (Decision 2: the install succeeded
and the library builds). It still says nothing about stack A, which
VST covers.

### Link check and Miri

- `link-check.log`: the library (rustc of the Rust nightly hax pins,
  overflow checks on) exports the seven `vu_*` functions. `caller.c`
  linked with it exits 0, and its output equals `expected.txt`,
  including re-entrancy (a) (`vu_fold_all` hands `vu_i_apply` to the
  client) and (b) (accessors called by name from the callouts). No
  proof is involved.
- `miri.log`: `client.rs` (run B) against `hax/src/lib.rs` and
  `ffi.rs`, with the one change `SUBJECT.as_ptr()` →
  `SUBJECT.as_ptr().expose_provenance()` (diff in the log). Status 0
  under Stacked Borrows and under Tree Borrows. Miri warns that
  `with_exposed_provenance` (`ffi.rs:173`) is an integer-to-pointer
  cast, under which it "might miss pointer bugs", and that Tree Borrows
  does not support such casts. So this run checks the hax glue's
  aliasing less strictly than run B's run checked Verus's and Aeneas's
  glue, whose subject is a real pointer. The cost comes from hax having
  no raw pointer type.

## Analysis

- Of the five milestone 3 verdicts, one is reached: hax's Rocq backend
  does not work at v0.5.0. Its output is ill-typed for any struct and
  any comparison. Four are pending: hax F\* and hax Lean, Creusot and
  RefinedRust. No toolchain failed to install, so none of them is
  "deferred" (Decision 2). They are pending because the disk floor
  refused their installs.
- hax's F\* output cannot be checked with an F\* other than the one
  hax pins: the 2026.11.15 release drops `FStar.Mul` and `--cmi`. The
  F\* backend therefore needs its own F\* of about 1 GB. It cannot share
  milestone 1's, contrary to the plan's first choice.
- The hax prototype costs 126 trusted lines, close to Aeneas's 122,
  which has the same design. hax has no raw pointers, so the subject
  address goes through integers. This weakens Miri's check of the glue,
  which Verus and Aeneas avoid.
- Disk is the binding constraint of runs C and D. After this run,
  18.5 GB are free. Under a 20 GB floor no further install is
  possible: Bedrock2, CN and RefinedC (run D) are blocked as well.
